Nsight Graphics 2026.4 新增了 MCP Server，AI agent 可以通过它采集 GPU Trace、读取 Graphics Capture，并查询性能数据。对已有自动化分析流程来说，它提供了一个统一的数据入口，可以减少手动操作 GUI、导出报表和解析文件的工作。

我用 2026.4.0 做了一轮试用，重点看它能否按 pass 取指标、定位 shader 热点，以及检查 draw 的状态。下面结合官方文档与这次试用记录，介绍两种接口模式和目前的限制。本文补入 11 月 15 日的每日推荐，内容于 11 月 17 日整理。

两种接口模式

官方将 MCP Server 标为 Alpha，2026.4 先在 Windows 提供。默认的 Workflow 面向常见任务，接口较少；Native 提供更细的检查和自动化能力，仍处于实验阶段。2026.4 更新说明

试用中的差别主要在数据粒度。Workflow 把帧、marker、指标和 draw 等整理成统一的表，适合查询整体信息。Native 则可以选择具体 marker 实例或时间范围，继续查询指标、shader 和图形状态。

例如，整段 trace 的平均吞吐无法直接回答某个阴影 pass 的瓶颈。需要先选中该 pass 的时间范围，再读取对应的 SM、L2、DRAM 等指标，减少整段平均值对局部瓶颈的掩盖。Native 在这一步提供了更合适的接口。

以下是本次 2026.4.0 试用观察：

操作 Workflow Native
控制采集起点与帧数 本次接口只能立即采一帧 可按帧或时间触发，并指定帧数
查询 pass 对应的硬件指标 只能取得整段 trace 的汇总值 可按 marker 实例或时间范围查询
检查 shader 热点 依赖已有 trace 包含 Shader Profiler 数据 可进一步缩小到热点 pass，并查询源码位置
检查 draw 参数与 pipeline 部分信息缺失，观察到实例数漏计 可读到实例数、深度附件、viewport 等状态
检查资源 本次查询的资源信息为空 可检查纹理、buffer 及其描述
对 draw 做 replay 计时 本次未取得 已取得逐 draw 耗时

因此，我暂时会把 Workflow 用于快速浏览，正式定位优先使用 Native。尤其是实例数和资源信息，不能因为接口返回了结果，就默认它完整可靠。

从 pass 查到源码

这次测试使用 RTX 4070 Ti、Vulkan 和瓶颈已知的小程序，覆盖 SSBO 带宽、分支发散、低占用延迟以及 early-Z / late-Z。小程序便于检查返回的数据是否符合预期，也减少了真实项目中多个问题相互影响的情况。

在分支发散用例中，Native 对应 marker 的“每条指令平均活跃线程数”为 4.04，SM 吞吐为 89.5%。已有分析工具读取的结果分别为 4.03 和 88.4%，两条读取路径得到的数值接近。结合已知的测试逻辑，较低的活跃线程数支持了线程利用不足的判断。

接着通过 Shader Profiler，查询定位到了 switch 分支对应的源码行。这样，分析流程就能从耗时 pass 继续走到具体 shader 和源码位置，再由开发者检查实现。

记录中还有一个容易误读的数值：Not Selected 占 68%。NVIDIA 对它的定义是 warp 已具备发射条件，但调度器选择了另一个 warp。单看这个比例不能证明分支发散，也不能直接当作可消除的等待时间。这里判断发散的依据应保留在测试逻辑、活跃线程数和源码分支上。Shader Profiler 指标说明

源码关联也取决于采集数据是否包含相应信息。没有源码或行号数据时，MCP 无法补出它们。

状态检查和重放计时

early-Z / late-Z 用例验证了另一条路径：先检查 draw 是否按预期提交，再比较其执行时间。

Native 返回了 16 个实例、D32 深度附件和 2560 × 1440 viewport，与测试设置一致。Replay 计时中，early-Z 用例的 draw 为 0.21 ms，写入 gl_FragDepth 的 late-Z 用例为 3.83 ms。这组结果描述的是本次测试程序中的两个 draw，不能推广为所有深度写入 shader 的固定代价。

状态和计时要一起看。只看较慢的 draw，无法排除实例数、深度状态或其他 pipeline 配置有误；先核对这些条件，再回到 shader 和指标，比较才有明确对象。

本次还验证了延迟采集：从启动程序、等待第 120 帧、采集 5 帧到写出文件，一次调用约需 5～7 秒。这是整个操作的耗时，包含等待应用运行的时间，不能当作 MCP 请求延迟。

数据仍需要分析方法

MCP 能返回计数器和状态，如何解释它们仍由分析流程负责。我的使用顺序会是先看 GPU 时间线是否存在空闲，再找耗时 pass，随后读取对应范围的吞吐、占用率和 stall，最后检查 shader 与 pipeline。

这些数据之间需要相互印证。吞吐较低可能与执行间隙、采样范围或依赖等待有关；某个 stall 比例高，也不代表消除它就能获得等比例加速。分析报告应保留所选时间范围、指标名称和关联 draw，让结论能够被复查。

试用记录还出现过硬件 draw 统计与目标程序 API 调用不一致的情况，并观察到吞吐结果波动。我会将这种样本标为待排查，检查后台 GPU 工作、上下文切换和采样范围，必要时重新采集。

官方说明，GPU Trace 中切换到其他进程上下文的区间可能没有采样数据；具体指标如何归属，需要结合采集模式和时间线判断。GPU Trace UI 说明

目前仍缺少的环节

本次 Native 工具目录中没有找到 Range Profiler、Pixel History 和 Shader Debugger 对应接口。逐 draw replay 可以帮助找出慢 draw，但还不能据此取得单个 draw 的完整硬件计数器；像素历史和单步调试仍需使用其他工具路径。这里说的是本次 MCP 暴露的能力，不代表 Nsight Graphics GUI 没有这些功能。

批量查询也比较繁琐。本次接口按“一个指标、一个时间范围”返回结果，查询 10 个 pass 的 7 项指标需要组织 70 次调用。跨帧平均、异常样本排除和 A/B 对比也要由外层程序完成。实际接入时，适合让脚本负责批量查询与统计，只把关键结果和证据交给 agent，避免在对话里反复搬运整表数据。

Shader 替换后的重放、远程测试机、D3D12 和真实游戏的 live 采集都还没有完成验证。记录中的既有项目 capture 和 Unity trace 分析，也不能替代这些场景的实测。

接入与使用建议

Windows 安装包中的 ngfx-mcp.exe 位于 host/windows-desktop-nomad-x64。默认启动后，兼容客户端可通过 Streamable HTTP 连接 http://127.0.0.1:7661/mcp；Native 的官方配置方式是让客户端启动该程序，并传入：

两种模式的工具名称和会话行为不同。接入时先读取当前工具清单，再选择调用方式，不能只切换传输协议。官方目前要求 agent 和服务端运行在同一台 Windows 机器上；本次尚未验证 Claude Code 的直接接入。MCP 接入说明

我的结论是，Native 已经值得作为日常性能分析的数据接口试用。它最有价值的部分，是把按范围查询指标、源码热点和 pipeline 检查连接到同一条自动化流程中。已有分析工具可以保留瓶颈判定和样本检查逻辑，逐步替换采集与数据读取部分，不必一次重写全部流程。

接入后仍应保存原始 capture、固定 Nsight 版本，并用已知用例检查关键字段。接口升级、字段缺失或采样异常都可能影响最终判断；一次能够顺利调用，不等于已经完成可靠性验证。

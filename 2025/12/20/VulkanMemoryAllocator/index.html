概述

Vulkan Memory Allocator (VMA) 是由AMD的GPUOpen项目开发的开源C++库,旨在简化Vulkan应用程序中GPU内存管理的复杂性。它通过提供高层次的API接口,将原本需要开发者手动处理的内存块管理、内存类型选择、对齐要求等底层操作进行了封装,极大地降低了Vulkan内存管理的难度。

官方链接:

  • GPUOpen VMA 主页
  • GitHub 仓库，本文基于 v3.3.0 版本

经典内存分配算法

在深入TLSF之前,了解传统内存分配算法的原理和局限性很有必要。这些算法是计算机科学的基础,也是理解TLSF优势的前提。

性能分析:

算法 时间复杂度 碎片特点 优点 缺点
First Fit O(n) 前端碎片堆积 简单,平均性能好 链表前部产生大量小碎片
Best Fit O(n) 产生大量微小碎片 内存利用率高 遍历慢,微碎片难以利用
Worst Fit O(n) 大块被快速消耗 剩余块较大 大块很快耗尽

线性分配算法会存在问题，从而不适合在对性能敏感的显存分配上使用：

  • O(n)时间复杂度在大量分配时性能差
  • 无法保证实时性,不适合每帧大量分配的场景
  • 碎片问题会随时间恶化

Buddy System

伙伴系统是一种经典的内存分配算法,Linux内核曾长期使用它管理物理页面。

核心原理:

  • 内存按2的幂次方大小管理
  • 分配时将大块二分,直到找到合适大小
  • 释放时检查”伙伴”(同一父块分裂出的另一半),如果空闲则合并

指标 值 说明

优缺点:

  • 优点:
    • 合并高效,外部碎片少
    • 实现简单,易于理解
    • 适合页面级别的大块内存管理
  • 缺点:
    • 内部碎片严重(最高50%)
    • 只能分配2的幂次大小
    • 不适合大小差异很大的分配请求

为什么不适合GPU内存管理:

  • GPU资源大小各异(纹理、缓冲区大小不固定)
  • 50%的内部碎片在GPU内存(通常几GB)中代价太高
  • O(log n)的分裂/合并开销在频繁分配时累积

Segregated Free Lists

隔离空闲链表是TLSF的直接前身,理解它有助于理解TLSF的设计思路。

核心思想

回顾之前的线性搜索算法(First Fit, Best Fit)的主要问题:需要遍历整个空闲链表来查找合适大小的块。

Segregated Free Lists的改进思路:

既然不同大小的分配请求都混在一个链表中查找效率低,那么预先按大小范围分类,将空闲块放入不同的”桶”(Size Class)中:

分类带来的优势:

  1. 快速定位: 请求128B时,直接计算应该在Class 3,跳过其他类别
  2. 减少搜索范围: 只需在Class 3的链表中查找,而不是遍历所有空闲块

分类策略:

通常使用对数分类或固定步长分类:

  • 小块(1-256B): 线性分类,步长16或32字节
  • 大块(256B+): 按2的幂次方分类 (256-512, 512-1024, 1024-2048…)

虽然空闲链表按大小分类可以加速查找,但释放内存时需要合并相邻的空闲块来减少碎片。空闲链表是按大小排序的,无法知道哪些块在物理内存中相邻,因此需要额外维护一个按地址顺序的物理链表。

数据结构设计

Segregated Free Lists使用双重链表结构来同时支持高效分配和合并:

Class 0-2 empty
Class 3 (65-128) B -> NULL
Class 4 (129-256) D -> E -> NULL
Class 5+ empty

空闲块查找

按内存大小分桶的方式会出现一种状况，某一个Class中可能存放了多个空闲块，而分配一块内存时，往往会发现不是所有的空闲块都能满足条件。

假设Class 4(129~256)中有多个不同大小的块，申请一块245B的内存时，可能会出现大部分的空闲块都不够大的情况。此时我们一般会使用Best Fit策略：

从第1个内存块开始遍历，直到找到一块满足大小的内存块

  • Segregated Free Lists按空闲内存块大小分类,但每个类的范围仍然很大
  • 如果需要精确匹配(Best Fit),就必须遍历链表，时间复杂度 O(n)
  • 遍历链表同时也会带来缓存不友好的情况，同时由于使用Best Fit策略，也会带来小小的碎片问题

TLSF算法原理

TLSF设计思想

TLSF (Two-Level Segregated Fit) 是一种专为实时系统设计的动态内存分配算法,由M. Masmano等人于2004年提出。

论文来源: “TLSF: a New Dynamic Memory Allocator for Real-Time Systems”
论文链接: http://www.gii.upv.es/tlsf/files/ecrts04_tlsf.pdf

核心特性:

  • O(1)时间复杂度: 分配和释放操作都在常数时间内完成
  • 低碎片率: 通常保持碎片率低于15%
  • 确定性: 适合实时系统,无最坏情况下的性能退化
  • 双层隔离: 使用两级位图结构加速空闲块查找

理解TLSF最好的方式是看它如何解决Segregated Free Lists的问题:

回顾: Segregated Free Lists的局限

TLSF的解决方案: 添加第二层细分

TLSF的核心思想是:在每个size class内部再次细分,让每个子区间的大小范围足够小,使得链表中的第一个块总是”足够好”的选择

双层分类机制详解

第一层: 粗粒度分类

第一层按2的幂次方划分内存类:

Class 0 Class 1 Class 2 Class 3 … Class N
内存大小 [0, 256) [256, 512) [512, 1024) [1024, 2048) [2^N …)
位表示 2^8 2^9 2^10 2^11 2^(N+8)
范围 256 256 512 1024 Doubling

计算公式(VMA实现):
直接获取最高位即可快速索引到对应Class

这里使用了BITSCAN_MSB指令,通过位扫描找到最高位出现的1，现代CPU上的指令通常只需1-3个CPU时钟周期,很好地避免了循环查找的开销。

第二层: 线性细分

这就是TLSF的关键创新: 对每个Memory Class进行线性细分成固定数量的子区间。

VMA使用SECOND_LEVEL_INDEX = 5,即每个内存类分成32个子区间 (2^5 = 32)。

Class 3的细分示例 (范围[1024, 2048),分成32份):

Memory Class 3 中存储了所有[1024, 2048) 大小的空闲内存块，第二层细分会将这些内存块再以每32B ((2048B - 1024B) / 32块) 为单位进行二次细分，从而再区分出 32 个区间出来。
其中每一个区间维护满足区间大小范围的空闲块链表。比如 Index 3 中存储所有大小在 [1120, 1152) 之间的空闲内存块。

最坏情况示例

可以看到 TLSF 通过位扫描得到的最相近的区域不一定都能满足需要分配的大小。当最坏情况发生时依旧会有一个链表遍历操作出现。所以TLSF不是绝对O(1),而是有界常数时间，因为区间划分的原因，链表长度会比较短。

分配策略

虽然TLSF已经最大限度减少了查找时间，但是最坏情况还是会存在链表遍历。所以实际使用时，可以通过修改分配策略来规避这一情况。
VMA中使用VmaVirtualAllocationCreateFlagBits对分配策略进行控制，指定为 MIN_TIME时，VMA分配时会为分配的内存大小再添加一个分区大小，从而直接从nextIndex开始查找
以1140举例的话，会直接以 1140 + 32 大小进行查找，变成直接跳过Index3，从Index4开始找可用内存块。这样做可以完全省掉链表遍历时间，但是会有一定的空间浪费。

算法对比总结

算法 分配时间 释放时间 内部碎片 外部碎片 确定性 适用场景
First Fit O(n) O(1) 低 高 差 简单场景,分配次数少
Best Fit O(n) O(1) 最低 中 差 内存紧张,分配次数少
Buddy System O(log n) O(log n) 高(50%) 低 中 页面管理,大块分配
Segregated Lists O(1)平均 O(1) 低 中 差 通用分配
Slab Allocator O(1) O(1) 0% 低 好 固定大小对象
TLSF O(1) O(1) 低 低 好 实时系统,GPU内存

粒度对比:

分配大小 Buddy粒度 TLSF粒度(32子区间)
64-128B 64B (100%) 2B (3%)
256-512B 256B (100%) 8B (3%)
1024-2048B 1024B (100%) 32B (3%)
4096-8192B 4096B (100%) 128B (3%)

TLSF的粒度随大小增长而增长,保持相对误差恒定在~3%,而Buddy始终是100%的2^n限制

TLSF是GPU内存管理的理想选择,因为它:

  • 满足实时性需求(真正O(1))
  • 支持任意大小分配(细粒度分类)
  • 保持低碎片率(<15%)
  • 提供确定性性能(无最坏情况退化)
  • 合并效率高(O(1)相邻块合并)

这就是为什么VMA的默认分配器(VmaBlockMetadata_TLSF)采用TLSF算法。

FreeList

VMA 使用一个全局的m_FreeList存储所有的空闲块链表，通过两级索引memoryClass和secondIndex计算对应空闲内存块在m_FreeList中的index。

由于二级分区是固定的32个分区，所以index直接用momoryClass * 32 + secondIndex 计算即可。

Class 0 的特殊处理:

对于 Class 0 [0, 256)，VMA采用固定的64B粒度来划分：

  • 256B再细分成32份太碎了
  • Vulkan的minMemoryMapAlignment通常要求64字节对齐
  • GPU缓存行通常也是64字节
  • 因此使用64字节粒度,只需要4个分区即可覆盖[0, 256)

所以上面 memoryClas >= 1 的计算会有一个 +4 的offset。

    • 例如: size = 1140 = 0b10001110100

设计理念

线性分配器使用双向量乒乓策略,支持多种分配模式:

  • SECOND_VECTOR_EMPTY: 只使用第一个向量,简单线性分配
  • SECOND_VECTOR_RING_BUFFER: 环形缓冲区模式
  • SECOND_VECTOR_DOUBLE_STACK: 双端栈模式

工作原理

Linear 分配器通过维护两个动态数组（Vector）来管理内存块，根据分配模式的不同，可以切换三种工作模式。

单向量模式

这是最简单的线性分配模式，所有分配从低地址向高地址增长，类似于栈分配器。

关键特性：

  • 只使用 m_Suballocations0 向量
  • 分配：直接在 offset 位置分配，然后 offset += size
  • 释放：标记为 FREE，但不回收空间
  • 重置：offset = 0，清空所有分配记录
  • 性能：分配 O(1)，仅需一次指针移动
  • 适用：每帧开始时完全重置的临时数据
环形缓冲区模式

单向量模式有个问题：一旦内存用完，即使前面的旧分配已经释放，也无法重新利用。环形模式解决了这个问题。

工作流程详解：

  1. 初始化空内存池

  2. Vector1 先填充：最初从地址 0 开始分配

  3. 不断分配新的内存块

  4. 释放内存块 (前400B释放，400-700B活跃，后324B空闲)

  5. 分配 100B 内存

  • 触发条件：当Vector1头部的旧分配被释放后，启用Vector2从地址0开始，重新利用已释放的空间。再分配内存块时会优先从 Vector2分配

BufferImageGranularity处理

基础概念

BufferImageGranularity是Vulkan规范中一个容易被忽视但极其重要的概念,它是GPU硬件的一个特性值,可通过VkPhysicalDeviceLimits::bufferImageGranularity获取。

根据 Vulkan 规范： 在同一内存块中，如果 Buffer 和 Image 共存（粒度通常是 64KB 或 128KB），它们之间可能产生冲突，导致未定义行为。

简单点说明就是，显存中每64KB的内存块中不能同时出现分配给Buffer的内存和分配给Image的内存。

示例问题场景：

当Buffer和Image在同一内存块中相邻分配时,为避免硬件缓存一致性问题,它们之间必须保持的最小对齐距离。典型值: 64KB、128KB、256KB或更大

Optimal Img ✓ ✓ ✗ ✗
FREE ✗ ✗ ✗ ✗

步骤：

  1. 冲突检测：

    • 计算新分配会落在哪个页（Page Index = offset / granularity）
    • 检查该页是否已有冲突类型的分配

  2. 偏移调整：

    • 如果有冲突，将 offset 向上对齐到下一个页边界
    • 公式：alignedOffset = VmaAlignUp(alignedOffset, granularity)

  3. 空间验证：

    • 检查调整后的 offset 是否仍在 block 的范围内
    • 验证：block.offset + block.size >= alignedOffset + allocSize

  4. Padding 处理：

    • Padding 不会被浪费，VMA 会将其复用：
      • 如果前一个块是 FREE → 扩展前一个空闲块的大小
      • 如果前一个块是 ALLOCATED → 创建新的小空闲块，插入到 FreeList

  5. 结果：

    • 成功：返回 true，使用调整后的 offset
    • 失败：返回 false，该 block 不适用

总结

VMA (Vulkan Memory Allocator) 通过精心设计的算法和数据结构，成功解决了Vulkan GPU内存管理的复杂性问题。以下是本文介绍的要点：

算法演进路径

从经典内存分配算法到TLSF，我们看到了一条清晰的优化路径：

  1. 线性搜索算法 (First/Best/Worst Fit)：实现简单但性能不可预测，O(n)复杂度无法满足实时系统需求
  2. Buddy System：引入快速合并机制，大量的内部碎片在GPU场景下代价过高
  3. Segregated Free Lists：通过按大小分类减少搜索范围，但每个类内部仍需遍历
  4. TLSF：双层细分 + 位图索引，分配时间和低碎片率的完美平衡

TLSF的核心优势

TLSF之所以成为VMA的默认分配器，源于其独特的设计：

  • 双层分类机制：第一层按2的幂次方粗分类（利用MSB位扫描），第二层线性细分32个子区间，将相对误差控制在3%
  • 位图加速查找：两级位图通过硬件位扫描指令实现常数时间查找，完全避免链表遍历
  • 策略灵活性：MIN_TIME策略可以牺牲少量空间换取绝对的时间保证，适应不同性能需求
  • 高效合并：物理链表 + 空闲链表的双重结构，使得相邻块合并也在O(1)时间完成

分配器的分工协作

VMA并非单一使用TLSF，而是根据使用场景选择合适的分配器：

分配器 适用场景 典型资源
TLSF 长期存活、随机分配释放 静态模型、纹理、Uniform Buffers
Linear 临时短期、批量释放 每帧动态顶点、Staging Buffers、粒子数据

BufferImageGranularity的优雅处理

VMA没有简单地禁止Buffer和Image混合分配，而是：

  1. 将内存按granularity大小划分页，记录每页的分配类型
  2. 在TLSF的CheckBlock流程中注入冲突检测逻辑
  3. 发现冲突时智能调整偏移到下一页边界
  4. 将对齐产生的padding复用为空闲块，避免空间浪费

这种设计在满足硬件限制的同时，保持了分配器的灵活性和低碎片率。

实际应用建议

在使用VMA时，理解这些底层原理可以帮助做出更好的决策：

  • 选择合适的分配策略：对性能敏感的代码路径使用MIN_TIME，对内存紧张的场景使用MIN_MEMORY
  • 合理规划资源类型：granularitySize过大时可以考虑区分使用多个显存池直接避免granularity冲突
  • 理解碎片来源：TLSF的碎片主要来自分区粒度（~3%）而非算法缺陷，这是可接受的trade-off
